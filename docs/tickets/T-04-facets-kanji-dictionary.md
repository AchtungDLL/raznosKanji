# ЧАСТЬ A. Грани WRITING и USAGE

## Проблема

Ядро уже открывает дополнительные грани: после `Balance.FACET_UNLOCK_THRESHOLD`
верных ответов по основной грани `WRITING` и `USAGE` становятся доступны,
и `pickFacet` честно их выбирает. Но интерфейс умеет задавать вопрос только
по одной грани — `MEANING`. Остальные открываются и не используются.

Из-за этого учебная единица работает одной стороной из трёх. Заказчик
формулировал её как связку: русское значение ↔ японское слово ↔ его запись.
Сейчас живёт только первая связь.

## WRITING — узнавание записи

Показывается **чтение каной и русское значение**. Игрок выбирает из четырёх
плиток **правильную запись слова** — ту, что с иероглифами.

Неверные варианты берутся из записей других слов. Приоритет отдаётся словам,
в записи которых есть **тот же иероглиф или похожий на него** (поле
`similar_looking` в `kanji.json`, связь `links.json`). Случайные записи — только
если подходящих не набралось.

Смысл именно в этом: различать 待つ и 持つ, а не отличать иероглиф от каны.
Подмена похожим — приём из экзамена, и данные для него уже лежат готовые.

Слова, записанные только каной (`word === reading`), по этой грани
**не спрашиваются**: у них нет записи, которую надо узнавать. Если такая
единица пришла с гранью `WRITING`, задай вместо неё `MEANING` — но
**не меняй `pickFacet`**, это чужая зона; обрабатывай на своей стороне.

## USAGE — употребление

Показывается **пример-предложение, в котором изучаемое слово заменено
пропуском**. Игрок выбирает из четырёх плиток слово, которое туда подходит.

Предложение и его перевод уже есть в данных (`sentence`, `sentence_ru`).
Перевод показывается **после ответа**, не до — иначе задание решается
переводом, а не пониманием.

Неверные варианты — другие слова, желательно той же длины и вида записи,
чтобы подстановка не отгадывалась по форме.

Если у слова нет примера (`sentence` пустой), грань `USAGE` для него
не спрашивается — поступай как с `WRITING` выше.

## Общее

Тип вопроса уже описан в контракте (`Question` в `types.js`): `facet`,
`prompt`, `expected`, `accepted`, `distractors`, `inputKind`. Пользуйся им,
не выдумывай свою структуру.

На экране боя должно быть видно, какая грань спрашивается — подпись над
вопросом уже есть, используй её.

# ЧАСТЬ B. Иероглифы как учебные единицы

## Зачем

Сейчас `kanji.json` в игре не используется вообще: обращений к нему ноль,
прогресс заводится только для слов. 2358 иероглифов, их чтения, радикалы,
похожие по начертанию наборы и связь с словами лежат мёртвым грузом.

## Правило появления

Иероглиф предлагается как учебная единица, **только когда игрок уже освоил
слово, в котором этот иероглиф встречается** — не меньше
`Balance.KANJI_UNLOCK_WORDS` таких слов. «Освоил» здесь значит, что слово
вышло из фазы изучения, то есть `interval > 0`.

Порядок принципиальный: сначала слово целиком, потом разбор знака внутри него.
Иероглиф в отрыве от слов — это списочная зубрёжка, от которой проект и уходит.

Связь «иероглиф → слова» готова в `links.json`, доступ — через
`wordsWithKanji(ch)` в `src/content/index.js`.

## Ограничение по данным, о котором нужно знать

Русское значение есть **не у всех** иероглифов: из 2358 заполнено 250.
В наборе для N4 (поле `jlpt` равно `"N5"` или `"N4"`, всего 284 знака)
русское значение есть у 185.

**Иероглиф без русского значения в игру не попадает.** Не подставляй вместо
него английское, не переводи сам, не выдумывай. Просто фильтруй: нет
`meaning_ru` — единица не создаётся. Недостающие переводы готовит постановщик.

## Вопросы по иероглифу

Заводи для иероглифа обычный `UnitProgress` с `kind: "kanji"` — контракт это
уже предусматривает. Единица проходит ту же фазу изучения и тот же SRS, что
и слово, отдельной логики не нужно.

Спрашивай двумя способами:

**Значение.** Показан иероглиф, выбрать русское значение из четырёх. Неверные
варианты — значения похожих по начертанию иероглифов
(`similar_looking`), их берётся `Balance.SIMILAR_DISTRACTORS` штук,
остальное добирается случайными.

**Слово.** Показан иероглиф, выбрать из четырёх слово, в котором он
встречается. Слова берутся из уже известных игроку — так вопрос опирается
на то, что он учил, а не проверяет незнакомое.

После ответа покажи справку: чтения (`on`, `kun`), радикал, и одно-два слова
из тех, что игрок уже знает.

# ЧАСТЬ C. Словарь

## Зачем

Игрок не видит, что он выучил. Нет ни списка слов, ни списка иероглифов,
ни возможности посмотреть, что придёт завтра. Для игры про накопление это
дыра: копить и не видеть накопленного бессмысленно.

## Что сделать

Новый экран со списком всего, что есть в прогрессе игрока. Для каждой единицы:

- запись, чтение, значение;
- состояние: изучается / интервал в днях / когда следующий показ;
- сколько раз показывалась и сколько раз срывалась.

Нужны:

- **поиск** по русскому значению, по чтению и по записи;
- **фильтры**: только слова / только иероглифы; изучается / на повторении /
  трудные (то, что ядро считает ветеранами — функция `isVeteran` в `srs.js`);
- **сортировка**: по сроку следующего показа и по частотности (`frequency`).

Список может быть длинным — 1497 записей. Рисуй порциями по мере прокрутки
или ограничивай выдачу, но **без внешних библиотек**.

Из словаря игрок должен видеть карточку единицы целиком: пример
с переводом, примечания, для иероглифа — чтения, радикал и слова с ним.

# ЧАСТЬ D. Свести концы

- В словаре и на стартовом экране числа обязаны сходиться: сколько единиц
  в прогрессе, сколько из них слов и иероглифов, сколько придёт завтра.
- Иероглифы участвуют в осаде наравне со словами — отдельной очереди для них
  не заводи.
- Квота новых единиц (`newQuota`) общая: иероглифы не добавляются сверх неё,
  а входят в неё. Иначе приток удвоится и весь расчёт нагрузки развалится.
